# Умный пешеходный переход

**Версия приложения: 1.1.0** · [История изменений](CHANGELOG.md)

Демонстрационный веб-прототип адаптивного управления пешеходным переходом. Он показывает, как наблюдения о дорожной обстановке могут влиять на переключение фаз светофора: контроллер учитывает плотность машин на размеченном участке, число ожидающих пешеходов, длительность их ожидания и доступность камеры.

> **Статус проекта:** прототип для демонстрации и экспериментов. Это не сертифицированный контроллер дорожного светофора. Расписание фаз и результаты на видео смоделированы; приложение не подключено к реальной камере, CV-системе или оборудованию.

## Что умеет приложение

- Показывает демонстрационную видеозапись и синхронные с ней посекундные наблюдения.
- Моделирует состояния цикла: зелёный для машин, предупреждение, защитный интервал, зелёный для пешеходов и интервал перед возвратом автомобилей.
- Сравнивает адаптивное управление с фиксированным циклом на одних и тех же наблюдениях.
- Показывает показатели движения, события, причины смены фаз и оценку времени ожидания.
- Показывает долю времени, когда проезд открыт транспорту, чтобы улучшение для пешеходов не скрывало цену для автомобильного потока.
- Позволяет запускать встроенные сценарии: обычный поток, час пик, большая группа пешеходов, пустая дорога и отказ камеры.
- Даёт менять параметры управления через интерфейс и API.
- Содержит вкладку «Симулятор» с детализированной 3D-моделью одной дороги и перехода, анимированным движением машин и пешеходов, настройкой обоих потоков, времени суток, типа дня и фаз, а также автоматическим пересчётом результатов. Настройки симулятора сохраняются в браузере.

### Поток данных

1. Интерфейс запрашивает список сценариев у `GET /api/scenarios`.
2. Для выбранного сценария отправляет конфигурацию контроллера в `POST /api/simulate`.
3. Backend проходит наблюдения по секундам, выбирает фазы, формирует события и сводную статистику.
4. Для видеоэпизода наблюдения загружаются из связанного JSON, а запись отдаётся через `GET /api/videos/{scenario_id}`.
5. FastAPI также раздаёт готовую frontend-сборку, поэтому для локального просмотра достаточно запустить один сервер.

### Логика контроллера

Цикл фаз: `vehicle_green` → `vehicle_yellow` → `all_red_to_pedestrian` → `pedestrian_walk` → `pedestrian_clearance` → `all_red_to_vehicle` → снова `vehicle_green`. Все защитные интервалы имеют отдельные настраиваемые длительности; отсутствие `CROSS` не сокращает освобождение перехода. Запрос может завершить автомобильный зелёный только после заданного минимума.

Адаптивный расчёт раз в секунду использует подтверждённые `track_id` людей с обеих сторон и уникальные ID машин в размеченном участке перед переходом. Время ожидания начинается при входе в зону, без 10-секундного статуса `WAIT`. Плотность `k = mean(vehicles_in_segment за 20 с) / segment_length_km`; вес одного человека `1 / (1 + k/k_ref)`; приоритет `N_waiting × weight + wait_s/t_max_s`. При приоритете от 1 запрос фиксируется до пешеходной фазы; после уверенного ухода всех людей его можно снять. Короткий пропуск ID до двух секунд не обнуляет время ожидания. Люди, пришедшие после начала `pedestrian_walk`, образуют следующий запрос.

`segment_length_km` задаёт длину участка **до** стоп-линии, `k_ref` — опорную дневную плотность в автомобилях/км для того же участка и числа полос, `t_max_s` — предел до **начала смены сигналов** (в демонстрации 90 с), `density_window_s` — окно сглаживания. Для калибровки сначала размечают геометрию и направления, измеряют одновременную занятость участка по дневным записям, затем выбирают и проверяют `k_ref`; интервалы зелёного, жёлтого и освобождения перехода утверждают по геометрии, скорости пешеходов и требованиям конкретного объекта. Демонстрационные значения нельзя автоматически переносить на реальный переход. Формулу `q/v_space` можно вычислять отдельно для диагностики по совпадающим окнам срезов и времени проезда; она не заменяет `k` и не используется для управления при остановившейся очереди или недостоверной скорости.

В симуляторе блок «Вес одного пешехода» показывает вес при текущей сглаженной плотности и расчётное время до запроса фазы, если ожидает только один человек и плотность не меняется: `t_max_s × (1 - weight)`. Рядом приведены случаи `k/k_ref = 0, 1, 3`. Это время **до запроса**, а не до зелёного сигнала: контроллер также соблюдает минимальный зелёный для машин и защитные интервалы. В ручном и резервном режимах вес не управляет переключением.

При потере наблюдений или состояния/времени фазы адаптивный запрос не отправляется: адаптер передаёт управление заранее заданному резервному циклу с обслуживанием пешеходов. В ручном режиме применяются заданные длительности фаз. Проверяемый `SimulatedController` реализует только виртуальные сигналы; интерфейс `ControllerAdapter` не задаёт протокол реального оборудования.

Готовый JSON видеозаписей содержит только агрегаты: его `vehicles` — максимум всех видимых машин за секунду. Поэтому он **не** передаётся в адаптивную формулу; для видеозаписи показывается резервный цикл и `null` для `n_waiting`, `vehicles_in_segment`, `k`, `weight`, `priority`. Это режим воспроизведения и проверки, не поток для управления в реальном времени.

## Быстрый запуск

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate        # Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -r backend/requirements.txt
npm --prefix frontend ci
npm --prefix frontend run build
python -m uvicorn backend.app.main:app --reload
```

Откройте <http://127.0.0.1:8000>. Документация API доступна на <http://127.0.0.1:8000/docs>, проверка доступности — <http://127.0.0.1:8000/api/health>.

### Интерактивный симулятор

Откройте вкладку «Симулятор», выберите «Свой поток» и задайте интенсивность машин и пешеходов, время суток и тип дня. Интенсивность машин задаётся суммарно для обоих направлений. Время и тип дня меняют расчётный спрос, а время суток также меняет освещение карты. Можно выбрать и готовый сценарий; изменение параметров потока переключит обратно на пользовательский. Выберите режим управления. В ручном режиме можно изменять длительность каждой из шести фаз; в адаптивном — минимальную автомобильную, пешеходную и фазу освобождения перехода, а также параметры приоритета. Изменения автоматически отправляются в `POST /api/simulate`; сцена, сигналы, шкала и показатели обновляются по одному ответу модели. Перемотка, пауза, повтор и скорость помогают сравнивать моменты. Сцена построена в Three.js: одна двусторонняя дорога с двумя размеченными полосами в каждом направлении, один пешеходный переход с островком безопасности, тротуары, знаки, светофоры, двенадцать фонарных столбов, две камеры на мачтах знаков, встречные машины и пешеходы. Машины едут по центрам полос; появления внутри секунды распределены равномерно по числу поступлений в ответе API. Придорожный знак на каждом подходе стоит перед автомобильным светофором по ходу движения. Пешеходы ожидают на разных местах тротуара, выходят с небольшим разбросом по времени и идут с разным темпом. Материалы, освещение и объёмные объекты приближают её к макету на фотографии. В переключателе «Обзор / Камера 1 / Камера 2» можно увидеть переход с каждой камеры, направленной на противоположный тротуар. Это ракурсы 3D-модели, а не поток с установленного оборудования. Общий вид можно вращать и приближать мышью. Поступления участников соответствуют расчёту сценария; траектории иллюстрируют его и не являются микроскопической транспортной моделью.

## API

### `GET /api/health`

Проверка: `{"status":"ok","source":"cv-json-and-simulation"}`.

### `GET /api/scenarios`

Возвращает `id`, название, описание, длительность и визуальный тип каждого сценария.

### `POST /api/simulate`

Пример запроса:

```json
{
  "scenario_id": "video",
  "config": {
    "control_mode": "adaptive",
    "min_vehicle_green": 10,
    "segment_length_km": 0.1,
    "k_ref": 20,
    "t_max_s": 90,
    "density_window_s": 20,
    "pedestrian_green": 8,
    "pedestrian_clearance": 6
  }
}
```

`scenario_id` принимает `video`, `normal`, `rush`, `group`, `empty`, `failure` или `custom`. Для `custom` передайте `profile` с `vehicle_rate` (0–120 авто/мин суммарно), `pedestrian_rate` (0–60 чел./мин), `time_of_day` (`morning`, `day`, `evening`, `night`) и `day_type` (`weekday`, `weekend`, `holiday`). По умолчанию используются 45 авто/мин, 30 чел./мин, день и будний день; эпизод длится 120 секунд. Ответ дополнительно содержит `profile.effective_vehicle_rate` и `profile.effective_pedestrian_rate` после поправки на условия. Валидация длительностей фаз действует и для пользовательского сценария. Режим `control_mode` — `adaptive` или `manual`; для ручного режима можно передать `phase_plan` с длительностями фаз. Ответ содержит покадровые результаты `frames`, журнал `events`, сводку `summary`, а для видео-сценария — результаты резервного цикла. `modeled_wait_difference` для видео равен `null`, поскольку адаптивное сравнение на агрегированной записи недостоверно.

### `GET /api/videos/{scenario_id}`

Возвращает MP4 выбранного заранее подготовленного видеоэпизода. Текущая запись доступна по `/api/videos/video`. Старый адрес `/api/video` сохранён для совместимости.

## Данные видео и CV

Файл `video_and_json/result_crosswalk.json` содержит 162 наблюдения — по одному на секунду новой записи. Формат и значения полей описаны в [CV_DATA_FORMAT.md](CV_DATA_FORMAT.md).

Чтобы подключить другой эпизод, подготовьте MP4 и JSON по этому контракту, положите их в корень проекта и добавьте одну запись в `VIDEO_EPISODES` внутри `backend/app/video_episode.py`. Backend автоматически включит эпизод в каталог API, а frontend возьмёт его `video_url`. Загрузчик файлов для этого не требуется.

Готовая запись показывает исходные наблюдения и виртуальный резервный цикл. Поведение людей и транспорта в ней уже зависело от реального светофора; она не позволяет сравнивать эффект адаптивного управления.

1. Создайте ветку от `main` для своей задачи.
2. Установите зависимости и запустите приложение по инструкции выше.

4. В описании pull request укажите, что изменилось, как это проверено и затрагивает ли изменение модель фаз или формат CV-данных.

## Ограничения и дальнейшие шаги

- Управление и светофор виртуальные; реальное оборудование и камеры не подключены.
- Наблюдения в демонстрационном JSON оценочные, метрики — иллюстративные.
- Доступность проезда показывает долю автомобильной зелёной фазы, но не заменяет модель задержки транспорта.
- Пороговые значения и фазы требуют инженерной, транспортной и нормативной валидации для конкретного перехода.
- Следующие направления: подключение результатов CV-команды, валидация данных, отдельные сценарии отказа и проверка модели с профильными специалистами.
